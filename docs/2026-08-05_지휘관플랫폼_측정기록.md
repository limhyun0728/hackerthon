# 지휘관 플랫폼 — 측정 기록과 결정 (2026-08-05)

월드모델 기반 지휘관 결심보조 플랫폼의 belief 표시, MAP-Elites descriptor, 월드모델
품질을 측정하고 고친 기록이다. 수치는 모두 실측이며 재현 명령어를 함께 남긴다.

---

## 1. 플랫폼 구조

```
전개안 격자   CEM 후보 → descriptor로 분류 → 셀별 elite 제시    백엔드: 월드모델(빠름)
추천 시나리오  결심마다 최고 점수 후보를 이어붙여 끝까지 전개      백엔드: DEVS(정확)
지휘관 선택   셀 하나를 고르면 그 계획을 DEVS로 6초 실행
결심 이력     트리로 보존, 되짚기 가능
```

결심 주기 6스텝(6초). 후보는 무작위 샘플링 — 최적안 하나를 찾는 게 목적이 아니라
가능한 전개의 폭을 보여주는 게 목적이다.

`--recommend-backend`를 DEVS로 둔 이유: 지휘관이 기준안으로 눈으로 보는 화면이라
벽 통과가 섞이면 안 된다.

## 2. 시뮬레이터 실측값 (모든 판정의 근거)

로그에서 직접 측정한 값이다. 화면 표시와 belief 계산의 상수는 전부 여기서 나온다.

```
BLUE 최대 이동속도   p99 1.500  max 1.501 유닛/초 = 15.0 m/s
RED  최대 이동속도   p99 1.000  max 1.001 유닛/초 = 10.0 m/s
관측거리             100m
유효 사거리          70m
유닛 실제 지름       0.7m
1 유닛               10m
1 스텝               1초
```

### 관측 판정과 사격 판정은 같은 규칙이다

`LosWorldAtomic.extTransition`은 `mode == ENGAGE` + `has_los` + 거리만 본다.
**시야각(FOV)을 안 본다.** `Soldier._engage`의 `visible_entities` 조회는 heading
회전용일 뿐, 없어도 `ammo -= 1; mode = ENGAGE`로 진행된다.

따라서 관측 표시에만 FOV를 요구하면 "주황(미관측)인데 사격선이 그려지는" 모순이
생긴다. 관측 판정에서 FOV를 뺐다.

```
관측(빨강/주황 구분)   거리 + LOS
후보 생성 게이트       거리 + LOS + 생존 + 탄약
시뮬레이터 피해 판정   거리 + LOS
```

## 4. RED 반응성 — 결심 주기의 한계

### 후보가 달라져도 RED 궤적은 같다

같은 초기 상태 + 서로 다른 BLUE plan 16개. 후보 축의 위치 표준편차:

```
              t+1s   t+2s   t+3s   t+4s   t+5s   t+6s
DEVS   RED    0.00m  0.00m  0.00m  0.00m  0.81m  0.81m
DEVS   BLUE   8.12m 11.28m 11.63m 13.11m 14.09m 14.09m
월드모델 RED  0.27m  2.20m  2.66m  2.64m  3.88m  3.84m
```

**DEVS에서 RED은 t+4초까지 정확히 0.00m — 완전히 같은 궤적이다.** 월드모델의 3.88m는
반응이 아니라 예측 잡음(자체 오차 27m)이다.

아카이브 10개 셀에서도 같다:

```
셀 간 RED 위치 표준편차   3.28m   ← 노이즈
셀 간 RED HP  표준편차    3.6     ← 태세와 연동

산발사격  → RED HP 475~479
교전      → RED HP 451~465
적극교전  → RED HP 451~454
```

**"적을 얼마나 깎았나"는 셀마다 다르고, "적이 어디로 갔나"는 전부 같다.**

원인은 `UrbanRedPolicy`가 lane을 따라가다 BLUE를 실제로 인지해야 반응하는데 6초는
그 전이라는 것. **축이나 descriptor의 문제가 아니라 지평선의 문제다.** 어떤 descriptor를
만들어도 RED 쪽 변별력은 안 나온다. 초반 시점 순위상관이 0 근처인 것과 같은 현상이다.

### 대응 방향

- **결심 주기를 늘린다** — 적 반응이 지평선에 들어옴. 단, 지휘관 개입 빈도가 줄어
  플랫폼 취지가 약해진다.
- **value head로 6스텝 너머를 접는다** — 주기를 유지하면서 장기 결과를 반영. 순위상관
  문제까지 같이 풀린다. (권장)

## 5. 고친 것

### 5.1 관측·사격 규칙 일치

관측에서 FOV를 제거해 사격 규칙과 맞췄다. 결과: 주황 표적에 그려진 사격선 0건 (26건 중).

### 5.2 재생 프레임에 관측 여부 태깅

`_build_path()`가 rollout 프레임에 `observed`/`last_seen`을 안 붙여, UI의
`u.observed === false`가 `undefined === false` → 거짓이 되어 **6초 재생 내내 모든 적이
빨간 점으로** 그려졌다. 예측이 어긋나는 건 재생 구간 안에서 벌어지는데 정작 그 구간이
가장 확실해 보이는 셈이었다.

- 프레임마다 `_observed_red_ids`로 판정, `belief_start`로 이전 결심의 `last_seen` 승계
- 아카이브 `rows`를 `path[-1]["units"]`로 바꿔 관측 이력이 세그먼트 사이에서 안 끊기게

검증: 근거리 배치 → 전 프레임 관측(3/3), 원거리 280m 배치 → 전 프레임 미관측(0/3),
원 반경 10m→60m로 성장.

### 5.3 불확실 원의 크기 근거

```
이전 : stale x 1.5(BLUE 속도) / mpp x 10, 상한 90px
       → 속도가 BLUE 값, 반경/지름 혼동으로 실제 절반 크기, 상한이 줌 의존
지금 : 반경 = min(100m, stale x RED_MAX_SPEED_MPS(10))
```

```
미관측     반경    화면 지름(zoom17)
  1초      10m       21px
  3초      30m       63px

```

시인성: 1px 점선 → 2px 점선 + 방사형 그라디언트 + 1.6초 맥동.

### 5.4 마커 크기

실축척 0.7m은 zoom17에서 0.74px이라 **zoom 19까지 하한이 곧 표시 크기**였다
(줌을 당겨도 안 커짐, zoom 20부터 축척 반영).

```

```

추정 유닛을 더 크게 두는 근거: 실축척은 "여기 정확히 있다"는 주장인데 추정 위치엔 그
주장이 없다. 정밀도는 원이 말하고 점은 중심만 찍는다.

### 5.5 MAP-Elites descriptor

**교전태세 — 전사자 제외**

```python
# 이전: 죽은 뒤 스텝의 명령까지 분자에 포함, 분모는 결심 시점 생존 수로 고정
#       → 일찍 전멸한 안이 가장 적극적으로 교전한 것처럼 보임
alive_start = concat([alive_now, alive_end[:-1]])   # k 시작 = k-1 끝
engage = ((types == ENGAGE) & issued & alive_start).sum() / alive_start.sum()
```

plan 축(BLUE 전용)과 slot 축은 순서가 달라 entity id로 매핑해야 한다.

**부대대형 — 절대 거리에서 변화 배율로**

```
이전 : 끝 시점 생존 BLUE 간 평균 쌍거리 (유닛)
지금 : 끝까지 살아남은 같은 집합의 끝/시작 비 (배율)

경계값  0.0    0.70    0.90    1.10    1.50
라벨   급속집결  집결   대형유지   산개   급속분산
```

핵심은 **양쪽을 같은 생존자 집합으로 잰다**는 것. 회귀 테스트:

```
바깥 유닛 전사, 나머지 정지  →  x1.00  대형유지   (이전엔 '밀집'으로 오분류)
바깥 전사 + 실제 집결        →  x0.25  급속집결
바깥 전사 + 실제 산개        →  x2.50  급속분산
생존 1명                     →  nan   대형유지로 접음
```

효과: 같은 후보 집합에서 **점유 셀 6개 → 10개**. 절대 거리가 초기 배치에 지배당해
후보 간 차이를 덮고 있었다.

### 5.6 기타

- 격자 셀에 BLUE HP 추가 (적HP만 있어 교환비를 못 읽었음)
- `measure_rank_correlation.py`에 `ROLLOUT_CHUNK_SIZE = 16` 청킹 — 후보 64개가

## 6. 미해결 / 결정 대기

### 6.1 불확실 원에서 관측 가능 영역을 깎아내기

**관측이 안 된다는 것 자체가 정보다.** 마지막 관측 지점에 있었다면 지금 보였을 테니
적은 거기 없다. 올바른 belief 영역:

```
belief = {도달 가능 범위} − {지금 관측 가능한 영역}
```

원의 중심이 가장 확실하게 비어 있는 자리다. 남는 건 건물 뒤나 관측거리 밖 — 건물
그림자 모양으로 파인 영역. 면적이 줄어 **100% 보증을 유지하면서 정보량이 는다.**

구현: 도달 범위에 격자를 깔아 각 점의 가시성(거리 + LOS)을 판정 후 캔버스/폴리곤으로
렌더. 관측 판정 함수는 이미 있다.

### 6.2 주황 점을 뺄 것인가

포함률 22.3%(t+1s), 이탈률 81.3%인 점을 어디에 찍든 없는 정밀도를 주장하게 된다.
원 밖에 찍히면 화면이 모순으로 보이고, 원 경계로 투영하면 우리가 만든 값을 모델 예측인
척 보여주게 된다. **원만 그리는 쪽이 정직하다.** 모델이 좋아지면 점을 다시 넣는다.

### 6.3 value head

설계는 정해져 있다 — 입력 = horizon 끝 slot batch, 출력 = 임무 결과 + 보조로 최종
BLUE/RED HP 비, Monte Carlo 라벨, layout 그룹화, 월드모델 encoder 동결.
§4의 RED 반응성 문제와 §3.1의 초반 시점 무상관을 동시에 겨냥한다.

# 추가 기록 2 (2026-08-06 후반)

## 13. 월드모델 예측은 자기회귀가 아니다

`rollout_cjepa_future`는 history 3프레임과 액션 전체를 넣고 **미래 `pred_frames`개를
한 번의 forward로 전부 뽑는다.** t+1을 t+2 입력으로 되먹이지 않는다.

```python
future_tokens = self.masked_predictor.inference(history_tokens, action_tokens=action_tokens)
# -> (B, pred_frames, N, D) 전 프레임 동시 산출
```

**결과 1 — horizon을 못 바꾼다.** `pred_frames`가 출력 텐서 모양에 박혀 있어 p10 모델에
horizon 6을 주면 `ValueError: action_features shape는 (B, T_total-1, U, ACTION_DIM)`이
난다. 모델마다 결심 주기가 고정이다 (p6=6초, p10=10초).

**결과 2 — 오차가 시간에 따라 안 자란다.** 자기회귀라면 t+1 오차가 t+2 입력을 오염시켜
누적되는데, 각 프레임이 독립적으로 history에서 나오므로 그렇지 않다.

```
p6  RED 오차   t+1s 13.3m -> t+6s 19.8m    거의 평평
```

장점이자 단점이다. 안정적이지만 **먼 프레임도 가까운 프레임과 같은 정보(history 3프레임)
만 보고 만든다.** t+6을 예측할 때 t+1~t+5에서 무슨 일이 있었는지를 쓰지 못한다.

> 앞서 "학습 맵에서는 lane을 외워서 이어도 안 틀린다"고 적은 것은 기전이 틀렸다.
> 자기회귀가 아니므로 "이어간다"가 아니라, 먼 프레임일수록 history만으로 추론할 폭이
> 커지고 학습 맵에서는 그 빈틈을 지형 기억으로 메우는 것이다. 결론은 같다.

같은 조건(30 시나리오 x 후보 16). p10은 `pred_frames=10`이라 horizon 10으로 굴리고

| --- | --- | --- | --- | --- |

```
p6    t+1s +18.8%   t+6s +29.8%     새 맵에서 나빠짐
```


10개 전체의 평균 오차를 줄이는 쪽으로 학습되므로 가까운 프레임에 집중할 이유가 없다.
플랫폼은 t+1~6을 쓰는데 p10은 그 구간이 약하다.

**결론: p6 확정.** 학습 맵 안에서 두 배 정확하고, p10을 쓰려면 결심 주기를 10초로 바꿔야
하는데 정확도를 절반 내주면서 그럴 이유가 없다.

## 15. p6의 실제 성능 — 좋지 않다

숫자를 있는 그대로 남긴다.

```
RED 예측오차 t+1s        13.3m      유닛 지름 0.7m, 골목 폭 수준
미관측 포함률 t+1s        37.7%      결심 직후 원 3개 중 2개가 빈 원
건물 통과                16.10%     단, 관통 깊이 p50 1.8m / max 5.3m
이동상한 초과             4.63%      최대 33.2 m/s (상한의 3.3배)
decoder 복원 오차         2.02m      표현 자체는 정확
```

**decoder가 2.02m인데 dynamics를 거치면 13.3m가 된다.** 상태를 읽는 능력은 있고 미래를
굴리는 데서 11m가 붙는다. 문제 지점이 분명하다.

시가지에서 13m는 "건물 뒤"와 "노출됨"이 갈리는 거리다. **"월드모델이 잘 된다"고 말하면
안 되고, "belief를 6초 단위로 대략 짚어주는 수준"이 정확한 표현이다.**

t+3s부터는 불확실 원이 90% 이상 덮으므로 결심 주기 단위로 보면 치명적이지 않다.

## 16. 학습 데이터 규모 — 병목은 윈도우가 아니라 지형

```
p6 계열 누적 (replay 200 + r2 184 = 384 에피소드)
  states            21,933      규칙 정책이 실제로 지난 궤적
  rollout_windows   52,560      각 tick에서 무작위 후보 16개를 DEVS로 굴린 것
  합계              74,493 윈도우
```

윈도우 수는 적지 않으나 **실질 다양성이 낮다.**

```
서로 다른 지형      5개        <- 74,493 윈도우 전부가 이 위에 있다
서로 다른 초기 배치  384개
서로 다른 궤적      384개      규칙 정책이라 배치가 정해지면 결정적
```

replay 52,560개는 384개 궤적 위의 각 시점에서 **액션만 흔들어본 것**이다. 상태 분포는
규칙 정책이 지나간 좁은 관 안에 머문다.

**같은 계산 비용이면 에피소드를 늘리는 것보다 맵을 늘리는 게 낫다.** 홀드아웃 측정이
병목을 지형으로 특정했다. 맵 생성은 VWorld 호출 몇 초, 에피소드 생성은 학습을 끄면
8초/개로 싸다.

## 17. 플랫폼의 CEM은 CEM이 아니다

**호출부마다 다르다. 이 절은 플랫폼 얘기다.**

| 호출부 | num_iterations | 성격 |
| --- | --- | --- |
| `commander_platform.py:572` | **1** | 무작위 샘플링 (이 절의 대상) |
| 학습 루프 `--cem-iterations` | 3 (기본) | 실제 CEM 반복 |
| 측정 스크립트 4개 | 1 | 의도적 — 최적화하면 분포가 좁아져 오차 측정이 왜곡된다 |

CEM의 본질은 "샘플 -> 상위 elite로 분포 갱신 -> 재샘플"인데 **1회면 갱신이 한 번도
일어나지 않는다.** 초기 분포에서 한 번 뽑고 끝이라 순수 무작위 샘플링이다.

플랫폼이 1을 쓰는 것 자체는 의도적이다 — 최적안 하나를 찾는 게 아니라 전개의 폭을
보여주는 게 목적이라 수렴시키면 안 된다. 문제는 아래에서 보듯 **prior가 좁아서 폭도
안 나온다**는 것이다.

다만 prior에 구조는 있다:

```python
for step_index in range(horizon):
    alpha = (step_index + 1) / horizon
    move_mean[step] = current_xy + alpha * (objective_xy - current_xy)   # 목표까지 선형 보간
# initial_move_std = 0.45 (4.5m) 흔들림, 사격 표적은 균등
```

**그래서 모든 후보가 목표 쪽으로 간다.** 차이는 4.5m 흔들림과 사격 대상뿐이다.
측정과 정확히 맞물린다:

```
셀 간 RED 위치 표준편차   3.28m    후보가 달라도 전황이 안 바뀜
셀 간 RED HP  표준편차    3.6      사격 대상만 다름
```

**"우회 기동", "한 부대 고착 + 다른 부대 측면" 같은 안은 이 prior에서 나올 수 없다.**
선형 보간 평균에서 4.5m 흔들어 도달할 수 있는 행동이 아니다.

### 세 갈래

- **iterations를 늘린다** — 진짜 CEM이 되지만 점수 좋은 쪽으로 수렴해 **다양성이 준다.**
  지휘관에게 폭을 보여주려는 목적과 반대다.
- **prior를 넓힌다** — `initial_move_std`를 키운다. 다양성은 늘지만 무의미한 후보도 는다.
- **구조를 넣는다** — 부대를 나눠 서로 다른 경유점을 준다. "좌측 우회 / 정면 / 우측 우회
  x 교전 강도"처럼 **전술 어휘를 먼저 정하고 그 안에서 흔든다.** (권장)

세 번째가 목적에 가장 맞고, MAP-Elites 축도 그때 비로소 의미를 갖는다. 지금은 축이
좋아도 채울 후보가 비슷해서 셀이 안 갈린다.

## 18. value head — 학습 완료, 홀드아웃 통과

### 18.1 라벨 = 임무 달성도 (mission_completed의 연속 완화)

`mission_completed()`의 불리언 조건을 그대로 완화한다. **임의 가중치가 없다.**

```
destroy = 1 - red_hp_최종 / (red_초기수 x 100)                   not red_alive 의 완화
reach   = 1 - min(1, max(0, 거리 - OBJECTIVE_RADIUS) / 10.0)     objective_reached 의 완화

DESTROY_ALL         progress = destroy
REACH_OBJECTIVE     progress = reach
HOLD_OBJECTIVE      progress = reach
DESTROY_AND_REACH   progress = min(destroy, reach)      AND 조건의 완화
BLUE 전멸           progress = 0                        원 조건의 하드 게이트
```

`min()`을 쓴 이유: AND 조건이라 둘 다 1이어야 1이다. 가중 평균을 쓰면 "적은 다 잡았지만
목표에 못 갔다"가 0.5로 나와 실패를 절반의 성공으로 오독한다.

**척도 10.0은 관측거리(100m)다.** 처음에 맵 반폭 20을 썼는데 근거가 없었다 — 실제 종료
거리가 p25~p75 = 2.3~4.0유닛에 몰려 있어 대부분 0.85~0.95로 압축되고 변별력이 죽었다.

```
TIMEOUT 안 표준편차      scale=20  ->  scale=10
  reach_objective        0.151        0.275     1.8배
  hold_objective         0.070        0.141     2배
```

## 18.7 다음 단계 — V로 CEM 채점하는 policy iteration 루프

지금까지 CEM으로 에피소드를 만들지 않은 이유는 **평가함수가 너무 휴리스틱해서 좋은 것을
배우기 어려웠기** 때문이다. V가 생겼으니 그 자리를 대체할 수 있다.

### 구조

```
액션 선택   DEVS rollout + V(6스텝 끝 상태) 채점      <- 월드모델을 안 거침
월드모델    그렇게 모인 데이터로 계속 학습             <- 더 넓은 분포를 봄
V           새 에피소드로 재학습                      <- V^π' 로 갱신
                         |
                         +-- 반복
```

**월드모델 오차(13.3m)가 액션 선택에 개입하지 않는다.** DEVS로 정확히 굴린 뒤 그 끝
상태만 V로 평가하므로, 바꾸는 것은 "무엇을 좋다고 볼 것인가" 하나뿐이다.

정당한 policy iteration이다.

```
π_rule 데이터 -> V^π_rule 학습
CEM이 V로 액션 선택 -> π' (1-step improvement)
π' 데이터 -> V^π' 학습 -> 반복
```

### 필요한 변경 (부품은 이미 있다)

```
--blue-controller cem        이미 선택지에 있음 (choices=("rule","cem"))
--rollout-backend devs       이미 선택지에 있음 (choices=("jepa","devs"))
episodic_cem_training_loop.py:1349
  scores = score_future_features_torch(...)   ->   V(끝 상태)
```

### 기대 효과

- **데이터 분포가 넓어진다.** §16의 병목 — 74,493 윈도우가 규칙 정책이 지나간 좁은 관
  안에 있다는 것 — 이 직접 풀린다.
- **라벨 쏠림이 완화된다.** TIMEOUT 81%에서 WIN이 늘어 달성도 분포가 고르게 퍼진다.
- 월드모델도 규칙 정책이 안 가는 상태를 보게 된다.

### 걸리는 것 세 가지

**V의 오차를 CEM이 파고들지만 발산하지는 않는다.** 모델 기반 RL의 전형적 실패는 V로 V를
갱신할 때(TD 부트스트랩) 일어난다. 여기는 라벨이 부트스트랩이 아니다.

```
CEM이 V를 믿고 액션 선택 -> DEVS로 끝까지 실행 -> 라벨 = 실제 최종 달성도 (Monte Carlo)
                                                   ^ 진실. V가 개입하지 않는다
```

V가 어떤 상태를 과대평가하면 CEM이 그리로 가고, 결과가 실제로 나빠서 라벨이 "여기는
나쁘다"로 붙는다. **오차가 있는 곳으로 CEM이 데려다주므로 정정이 필요한 지점에 정확히
표본이 생긴다.** 능동적 데이터 수집에 가깝다.

남는 위험은 발산이 아니라 **속도와 진동**이다.
- 정정에 라운드 하나(3~5시간)가 든다. V가 크게 틀린 채 시작하면 그 라운드를 통째로
  나쁜 궤적 모으는 데 쓴다.
- V가 영역 A를 고치면 CEM이 영역 B로 옮겨가고 거기서도 과대평가면 다시 B를 고치는
  식으로 순회할 수 있다.
→ 완화: 후보의 절반만 V 상위에서 뽑고 나머지는 기존 prior에서 뽑는다.
   (1349행 근처에 이미 `top_count = count // 2`로 절반만 상위를 쓰는 구조가 있다)

**라운드마다 V를 재학습해야 한다.** π가 바뀌면 V^π도 바뀐다. 이전 V를 계속 쓰면 몇 번
돌다가 어긋난다. 17만 파라미터라 몇 분이면 된다.

**다양성이 줄어든다.** 학습 데이터로는 좋은 궤적이 나으니 문제없지만, 같은 CEM 구성을
플랫폼에도 쓰면 지휘관에게 보여줄 폭이 사라진다. **학습용과 표시용 설정을 분리해야 한다.**

### 규모

```
1라운드 = 에피소드 200개 (CEM+DEVS) + 월드모델 학습 + V 재학습
라운드당 3~5시간, 의미 있는 개선을 보려면 3~5라운드
```

시연 전에 할 일은 아니다. 방향은 맞고 지금 만든 V가 출발점이 된다.

## 21. 코드 수정 완료 — policy iteration 루프

### 21.1 무엇을 바꿨나

**액션 샘플링 구조** (`worldmodel/cem_planner.py`)

고정 prior에서 스텝/유닛마다 독립 추출하면 30회 추출의 큰 수 법칙으로 집계 비율이
prior 평균에 몰린다. 실측에서 후보의 79%가 교전태세 격자 한 칸에 들어가 MAP-Elites가
1칸만 썼다. **prior 값을 바꿔도 몰리는 위치만 옮겨갈 뿐 퍼지지 않는다.**

```python
CANDIDATE_MIX_ALPHA = (0.25, 0.45, 0.28, 0.02)   # STOP/MOVE/ENGAGE/TURN, Sigma alpha=1.0
STICKINESS_RANGE    = (0.3, 0.8)
```

후보마다 Dirichlet에서 **시작/끝 분포를 각각 뽑아 보간**한다. 비율 분산과 국면 순서가
동시에 생긴다(시작 MOVE 우세 + 끝 ENGAGE 우세 = 접근 후 교전). 전술 어휘를 손으로
정하지 않고 두 끝점 추출에서 나오게 한다.

**점착성이 따로 필요하다.** 보간만으로는 스텝별 추출이 여전히 독립이라 구간이 안
길어진다(1스텝 구간 59% -> 64%로 오히려 악화). 직전 액션을 확률 s로 이어가야 늘어난다
(1스텝 구간 35%, 평균 구간 2.62).

| | 전체 비율 | ENGAGE 표준편차 | MOVE 평균 구간 |
| --- | --- | --- | --- |
| 이전 (고정 prior) | 20/50/25/5 | 0.080 | 1.72 |
| 지금 (Dirichlet+점착) | 25/45/28/2 | 0.202 | 2.62 |

교전태세 5칸: `0/10/79/11/0%` -> `15/27/24/21/13%`
**MAP-Elites 2차원 23/25칸 점유, 최대 집중도 10%** (이전 셀 4~10개)

**MOVE 목적지** — 연속 MOVE 구간마다 그 시점 위치에서 예산(구간길이 x 1.5) 안
자유공간 균등 추출.

```
이전  목표까지 직선 보간 + 가우시안 -> 건물 안 37.4%, 도달가능 43.5%
지금  건물 안 0.0%, 도달가능 100.0%
```

기준점이 **그 시점 위치**여야 한다. 6개 목적지를 전부 계획 시작 위치 기준으로 뽑으면
세 번째 MOVE를 "시작 위치에서 4.5유닛" 안에서 고르는데 그때 유닛은 다른 곳에 있다.
연속 구간은 목적지 하나를 공유해야 3스텝짜리 기동이 성립한다.

> 자유공간 점을 뽑은 뒤 거리로 자르면 안 된다. 잘린 지점이 건물 안에 떨어져 44%로
> 악화됐다. 유닛마다 거리순 정렬해 두고 예산 안 구간에서만 골라야 한다.

**6스텝 커밋** (`episodic_cem_training_loop.py`)

매 tick 재계획하면 6스텝 시퀀스를 뽑는 의미가 절반만 남는다. lookahead로 채점에는
쓰이지만 **구조(국면, 연속 구간)가 첫 스텝만 실행되고 버려진다.** 플랫폼은 지휘관이
고른 계획을 6초 동안 그대로 집행하므로 학습을 매 tick으로 두면 데이터가 실제 실행
방식과 다른 분포에서 나온다. 비용도 6배다(에피소드 5시간 -> 8~25분).

**V로 CEM 채점** (`worldmodel/value_scoring.py`)

DEVS로 정확히 굴린 뒤 끝 상태만 V로 평가한다. 월드모델 오차가 액션 선택에 개입하지
않는다.

**온라인 V 학습** (`worldmodel/value_online.py`)

월드모델과 **같은 데이터를 공유하되 손실은 따로**. 라운드로 나눌 이유가 없다 — V의
라벨은 episode가 끝나는 순간 나오므로 월드모델과 같이 매 episode 학습하면 된다.

버퍼가 필요한 이유: 한 episode의 표본은 라벨이 전부 같다. 그것만으로 여러 epoch를
돌리면 매번 같은 답을 외운다. 월드모델은 window마다 라벨이 달라 이 문제가 없다.

표본은 **t >= horizon 인 상태에서만** 뽑는다. 플랫폼에서 V가 보는 것은 6스텝 지평선의
끝 상태(t=6,12,18...)이므로 그보다 이른 상태는 추론에 나타나지 않는다.

V는 규칙 기반 데이터로 이미 학습돼 있으므로(val MAE 0.1388) **처음부터 CEM 채점에
쓴다.** 휴리스틱 대기 구간이 없다.

### 21.2 새 인자

```
--value-head-checkpoint         warm start
--value-epochs-per-episode 3
--value-batch-size 16           32이면 버퍼가 차기까지 학습이 안 돈다
--value-samples-per-episode 10
--value-buffer-episodes 30
--value-min-episodes 10
--value-head-output-path        생략하면 <checkpoint>_value.pt
--cem-candidates 32 --cem-elites 8 --cem-iterations 3
```

후보 수는 측정으로 정했다 — 32에서 64로 가면 최고 V가 1.6% 좋아지는데 비용은 2배다
(1개 대비 32개가 +14.8%, 64개가 +16.6%, 128개가 +18.0%).

### 21.3 보조 라벨은 빼는 것이 낫다

```
aux-weight 0.0   best val MAE 0.1388
aux-weight 0.3   0.1407
```

`outcome` 3-class는 다수결 기준선(0.833)과 동률이라 배울 게 없는데 gradient만 쓰고,
`red_hp_ratio`/`objective_gap`은 달성도 정의에 이미 들어간 정보다.

### 23.1 스모크 재확인 (10분)

`--value-batch-size 16`으로 V 학습이 실제로 도는지(`steps>0`) 확인한다.

### 23.2 V 채점이 값어치가 있는지 (필수)

**같은 조건에서 규칙 기반과 CEM+V의 임무 달성도를 대조한다.** 이걸 안 재면 전체 구조가
개선인지 알 수 없다. 스모크에서 progress가 0.000~0.150으로 낮았는데, 3v5~3v6 수적
열세 때문인지 V 채점이 나빠서인지 구분이 안 된다.

### 23.3 검증셋 생성 (CEM, 12시간)

검증 window는 디스크 로그(실제 집행된 궤적)에서만 만들어진다. replay window는 메모리에만
있고 저장되지 않으므로, **규칙 기반으로 만들면 검증 액션이 전부 규칙 정책 것이 된다.**
액션 분포를 맞추려면 CEM으로 생성해야 한다.

```bash
python -u worldmodel/episodic_cem_training_loop.py   --device cuda:0 --freeze-world-model   --world-model-checkpoint checkpoints/cjepa_p6_r2_best.pt   --value-head-checkpoint checkpoints/value_head.pt   --value-batch-size 16   --blue-controller cem --cem-rollout devs   --cem-candidates 32 --cem-elites 8 --cem-iterations 3   --obstacle-configs <학습 10개 맵>   --history-frames 3 --pred-frames 6 --rollout-replay-per-tick 0   --episodes 30 --duration 60.0 --seed 5555   --blue-team-size-min 1 --blue-team-size-max 10 --red-team-size-max 10   --mission-types destroy_and_reach destroy_all reach_objective hold_objective   --checkpoint-path checkpoints/_throwaway_val10.pt   --value-head-output-path checkpoints/_throwaway_val10_value.pt   --output-root output/validation_cem10
```

기존 검증셋 100개(`validation_shared`, `_v2`)는 5개 맵 것이라 버린다.
