# 지휘관 플랫폼 — 측정 기록과 결정 (2026-08-05)

월드모델 기반 지휘관 결심보조 플랫폼의 belief 표시, MAP-Elites descriptor, 월드모델
품질을 측정하고 고친 기록이다. 수치는 모두 실측이며 재현 명령어를 함께 남긴다.

---

## 1. 플랫폼 구조

```
전개안 격자   CEM 후보 → descriptor로 분류 → 셀별 elite 제시    백엔드: 월드모델(빠름)
추천 시나리오  결심마다 최고 점수 후보를 이어붙여 끝까지 전개      백엔드: DEVS(정확)
지휘관 선택   셀 하나를 고르면 그 계획을 DEVS로 6초 실행
결심 이력     트리로 보존, 되짚기 가능
```

결심 주기 6스텝(6초). 후보는 무작위 샘플링 — 최적안 하나를 찾는 게 목적이 아니라
가능한 전개의 폭을 보여주는 게 목적이다.

`--recommend-backend`를 DEVS로 둔 이유: 지휘관이 기준안으로 눈으로 보는 화면이라
벽 통과가 섞이면 안 된다.

## 2. 시뮬레이터 실측값 (모든 판정의 근거)

로그에서 직접 측정한 값이다. 화면 표시와 belief 계산의 상수는 전부 여기서 나온다.

```
BLUE 최대 이동속도   p99 1.500  max 1.501 유닛/초 = 15.0 m/s
RED  최대 이동속도   p99 1.000  max 1.001 유닛/초 = 10.0 m/s
관측거리             100m
유효 사거리          70m
유닛 실제 지름       0.7m
1 유닛               10m
1 스텝               1초
```

### 관측 판정과 사격 판정은 같은 규칙이다

`LosWorldAtomic.extTransition`은 `mode == ENGAGE` + `has_los` + 거리만 본다.
**시야각(FOV)을 안 본다.** `Soldier._engage`의 `visible_entities` 조회는 heading
회전용일 뿐, 없어도 `ammo -= 1; mode = ENGAGE`로 진행된다.

따라서 관측 표시에만 FOV를 요구하면 "주황(미관측)인데 사격선이 그려지는" 모순이
생긴다. 관측 판정에서 FOV를 뺐다.

```
관측(빨강/주황 구분)   거리 + LOS
후보 생성 게이트       거리 + LOS + 생존 + 탄약
시뮬레이터 피해 판정   거리 + LOS
```

## 4. RED 반응성 — 결심 주기의 한계

### 후보가 달라져도 RED 궤적은 같다

같은 초기 상태 + 서로 다른 BLUE plan 16개. 후보 축의 위치 표준편차:

```
              t+1s   t+2s   t+3s   t+4s   t+5s   t+6s
DEVS   RED    0.00m  0.00m  0.00m  0.00m  0.81m  0.81m
DEVS   BLUE   8.12m 11.28m 11.63m 13.11m 14.09m 14.09m
월드모델 RED  0.27m  2.20m  2.66m  2.64m  3.88m  3.84m
```

**DEVS에서 RED은 t+4초까지 정확히 0.00m — 완전히 같은 궤적이다.** 월드모델의 3.88m는
반응이 아니라 예측 잡음(자체 오차 27m)이다.

아카이브 10개 셀에서도 같다:

```
셀 간 RED 위치 표준편차   3.28m   ← 노이즈
셀 간 RED HP  표준편차    3.6     ← 태세와 연동

산발사격  → RED HP 475~479
교전      → RED HP 451~465
적극교전  → RED HP 451~454
```

**"적을 얼마나 깎았나"는 셀마다 다르고, "적이 어디로 갔나"는 전부 같다.**

원인은 `UrbanRedPolicy`가 lane을 따라가다 BLUE를 실제로 인지해야 반응하는데 6초는
그 전이라는 것. **축이나 descriptor의 문제가 아니라 지평선의 문제다.** 어떤 descriptor를
만들어도 RED 쪽 변별력은 안 나온다. 초반 시점 순위상관이 0 근처인 것과 같은 현상이다.

### 대응 방향

- **결심 주기를 늘린다** — 적 반응이 지평선에 들어옴. 단, 지휘관 개입 빈도가 줄어
  플랫폼 취지가 약해진다.
- **value head로 6스텝 너머를 접는다** — 주기를 유지하면서 장기 결과를 반영. 순위상관
  문제까지 같이 풀린다. (권장)

## 5. 고친 것

### 5.1 관측·사격 규칙 일치

관측에서 FOV를 제거해 사격 규칙과 맞췄다. 결과: 주황 표적에 그려진 사격선 0건 (26건 중).

### 5.2 재생 프레임에 관측 여부 태깅

`_build_path()`가 rollout 프레임에 `observed`/`last_seen`을 안 붙여, UI의
`u.observed === false`가 `undefined === false` → 거짓이 되어 **6초 재생 내내 모든 적이
빨간 점으로** 그려졌다. 예측이 어긋나는 건 재생 구간 안에서 벌어지는데 정작 그 구간이
가장 확실해 보이는 셈이었다.

- 프레임마다 `_observed_red_ids`로 판정, `belief_start`로 이전 결심의 `last_seen` 승계
- 아카이브 `rows`를 `path[-1]["units"]`로 바꿔 관측 이력이 세그먼트 사이에서 안 끊기게

검증: 근거리 배치 → 전 프레임 관측(3/3), 원거리 280m 배치 → 전 프레임 미관측(0/3),
원 반경 10m→60m로 성장.

### 5.3 불확실 원의 크기 근거

```
이전 : stale x 1.5(BLUE 속도) / mpp x 10, 상한 90px
       → 속도가 BLUE 값, 반경/지름 혼동으로 실제 절반 크기, 상한이 줌 의존
지금 : 반경 = min(100m, stale x RED_MAX_SPEED_MPS(10))
```

```
미관측     반경    화면 지름(zoom17)
  1초      10m       21px
  3초      30m       63px
  6초      60m      127px   ← 결심 주기 한 사이클
 10초     100m      211px   (관측거리 상한)
```

시인성: 1px 점선 → 2px 점선 + 방사형 그라디언트 + 1.6초 맥동.

### 5.4 마커 크기

실축척 0.7m은 zoom17에서 0.74px이라 **zoom 19까지 하한이 곧 표시 크기**였다
(줌을 당겨도 안 커짐, zoom 20부터 축척 반영).

```
MIN_UNIT_PX      4 → 7
MIN_BELIEVED_PX  9 → 11
```

추정 유닛을 더 크게 두는 근거: 실축척은 "여기 정확히 있다"는 주장인데 추정 위치엔 그
주장이 없다. 정밀도는 원이 말하고 점은 중심만 찍는다.

### 5.5 MAP-Elites descriptor

**교전태세 — 전사자 제외**

```python
# 이전: 죽은 뒤 스텝의 명령까지 분자에 포함, 분모는 결심 시점 생존 수로 고정
#       → 일찍 전멸한 안이 가장 적극적으로 교전한 것처럼 보임
alive_start = concat([alive_now, alive_end[:-1]])   # k 시작 = k-1 끝
engage = ((types == ENGAGE) & issued & alive_start).sum() / alive_start.sum()
```

plan 축(BLUE 전용)과 slot 축은 순서가 달라 entity id로 매핑해야 한다.

**부대대형 — 절대 거리에서 변화 배율로**

```
이전 : 끝 시점 생존 BLUE 간 평균 쌍거리 (유닛)
지금 : 끝까지 살아남은 같은 집합의 끝/시작 비 (배율)

경계값  0.0    0.70    0.90    1.10    1.50
라벨   급속집결  집결   대형유지   산개   급속분산
```

핵심은 **양쪽을 같은 생존자 집합으로 잰다**는 것. 회귀 테스트:

```
바깥 유닛 전사, 나머지 정지  →  x1.00  대형유지   (이전엔 '밀집'으로 오분류)
바깥 전사 + 실제 집결        →  x0.25  급속집결
바깥 전사 + 실제 산개        →  x2.50  급속분산
생존 1명                     →  nan   대형유지로 접음
```

효과: 같은 후보 집합에서 **점유 셀 6개 → 10개**. 절대 거리가 초기 배치에 지배당해
후보 간 차이를 덮고 있었다.

### 5.6 기타

- 격자 셀에 BLUE HP 추가 (적HP만 있어 교환비를 못 읽었음)
- `measure_rank_correlation.py`에 `ROLLOUT_CHUNK_SIZE = 16` 청킹 — 후보 64개가
  33.6GB를 쓰고 14.55GB를 더 요청해 빈 GPU에서도 OOM

## 6. 미해결 / 결정 대기

### 6.1 불확실 원에서 관측 가능 영역을 깎아내기

**관측이 안 된다는 것 자체가 정보다.** 마지막 관측 지점에 있었다면 지금 보였을 테니
적은 거기 없다. 올바른 belief 영역:

```
belief = {도달 가능 범위} − {지금 관측 가능한 영역}
```

원의 중심이 가장 확실하게 비어 있는 자리다. 남는 건 건물 뒤나 관측거리 밖 — 건물
그림자 모양으로 파인 영역. 면적이 줄어 **100% 보증을 유지하면서 정보량이 는다.**

구현: 도달 범위에 격자를 깔아 각 점의 가시성(거리 + LOS)을 판정 후 캔버스/폴리곤으로
렌더. 관측 판정 함수는 이미 있다.

### 6.2 주황 점을 뺄 것인가

포함률 22.3%(t+1s), 이탈률 81.3%인 점을 어디에 찍든 없는 정밀도를 주장하게 된다.
원 밖에 찍히면 화면이 모순으로 보이고, 원 경계로 투영하면 우리가 만든 값을 모델 예측인
척 보여주게 된다. **원만 그리는 쪽이 정직하다.** 모델이 좋아지면 점을 다시 넣는다.

### 6.3 value head

설계는 정해져 있다 — 입력 = horizon 끝 slot batch, 출력 = 임무 결과 + 보조로 최종
BLUE/RED HP 비, Monte Carlo 라벨, layout 그룹화, 월드모델 encoder 동결.
§4의 RED 반응성 문제와 §3.1의 초반 시점 무상관을 동시에 겨냥한다.


**교훈**

- `CUDA_VISIBLE_DEVICES`와 `--device`를 섞지 말 것. 한쪽만 쓴다.
- 검증 배치는 학습 배치의 8배(64 vs 8)가 기본값이다. pred_frames를 늘리면 여기서 터진다.
- `tee`로 로그를 남길 것. 1·2회차는 traceback이 사라져 코드에서 역추적해야 했다.
- 기존 결과 파일을 `tee`로 덮지 말 것.
